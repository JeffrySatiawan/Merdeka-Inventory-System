# RCA — merdekainv.online (deployment `pdf-notify-sound`) post-deploy slow/timeout on DB endpoints

Run analyzed: `726c2b7c-1056-41e8-90ec-d6b603260c3a` (redeploy, status success)
Template: `nextjs_mongo_shadcn_base_image` (Next.js standalone, `node server.js` :3000, frontend_type=kubernetes)
Tier: tier_1 (CPU 250m req / 500m limit, 2Gi mem, 2 replicas) · DB: `pdf-notify-sound-cycle_count` (Atlas)

## Symptom
Users stuck on infinite loading at login. External curl confirms: non-DB paths fast (`/`=200/284ms, `/api/auth/me` no-token=401/0.26s, 404s fast, `/sw.js`=200), but every DB-touching path slow/timeout (`POST /api/auth/login` 17–20s, `/api/monitor` & `/api/dashboard` timeout >15s). Identical code on preview responds <0.5s.

## What I verified (evidence)
- **DB is healthy and fast from server-side** using the EXACT `MONGO_URL` secret the pod resolves: `list_collections` = 27 collections instantly; `count`/`find`/`list_indexes` all instant.
  - So RULED OUT: wrong/stale MONGO_URL secret, DB down, DNS-to-DB failure, auth mismatch. The secret is correct (same cluster, real data).
- **Data volumes are small and indexed** — so NOT a missing-index / collection-scan problem:
  - employees=8, sessions=169 (has unique `token` index), absensi_records=266, sku_history=4882, om_pdfs=7407 (indexed on `uploaded_at`, `deleted+uploaded_at`, unique `id`), tj_screenshots=9, backup_jobs=2. Projected find on om_pdfs returned instantly.
- **Pod logs are clean of Mongo errors.** Over 180 min the only error is a single `API error [Error: aborted] { code: 'ECONNRESET' }` — that is the external curl client aborting at its 15s timeout, not a driver error. There is **no** `MongoServerSelectionError`, no pool/WaitQueueTimeout, no "connection refused", no "topology destroyed". A genuinely broken connection would log these after serverSelectionTimeoutMS (30s default). Login completing in 17–20s (under 30s) and only sometimes timing out means queries ARE succeeding, just slowly/variably.
- **Could not inspect:** pod events/metrics and per-pod logs (tooling returns `cluster deployment-cluster-04: cluster not found` — platform-side), and eph sandbox failed to boot twice (`pod reached terminal phase Failed`). So pod CPU/memory and the source could not be directly instrumented.

## Most likely root cause (inferred, NOT reproduced)
The pod is paying a **new-connection cost on (nearly) every DB request** instead of reusing a cached MongoClient. On preview this is invisible because Mongo is `localhost` (no SRV, no TLS → reconnect ~instant). On production the URI is Atlas `mongodb+srv://`, so each new connection = DNS SRV lookup + TLS handshake + topology discovery = multiple seconds, intermittently brushing the serverSelection timeout. This precisely explains: DB-only slowness, prod-slow vs preview-fast, variable 17–20s with occasional hard timeouts, and the absence of outright driver errors.

Why it began with THIS "minor" deploy: moving `public/sw.js` → `lib/pwa/sw-source.js` and adding `app/sw.js/route.js` changes the Next.js module graph / chunking. In a Next.js standalone build that can break a Mongo connection singleton (e.g. the client is no longer shared via `globalThis`, or the db helper gets duplicated into a route chunk), turning a once-cached connection into per-request connects. A rebuild of the same source will reproduce it, so a plain redeploy will NOT fix it — this is why I did not burn a redeploy.

Alternative (secondary) possibility I could not fully exclude due to missing pod metrics: transient per-pod/node network or CPU-throttle degradation (500m CPU makes TLS handshakes costlier). If, after the code fix below, latency persists identically, revisit pod/node health and tier CPU.

## Fix (owner: Code — E1 to apply in source, then redeploy)
1. **Enforce a single cached MongoClient across the standalone server.** Cache the client/promise on `globalThis` (not a module-local `let`) and reuse it in every route/handler and server action. Verify the db-connection module is imported the same way everywhere and isn't duplicated into a per-route chunk after the file move. Remove any per-request `new MongoClient()` / `client.connect()` in hot paths.
2. **Bound connection cost:** set `serverSelectionTimeoutMS` (e.g. 5000) and `connectTimeoutMS`, and set `maxPoolSize`/`minPoolSize` (minPoolSize≥1 to keep a warm connection) so cold pods pre-warm and fail fast instead of hanging ~17–20s.
3. **Confirm the trigger:** diff the module imports of the db helper before/after the `public/sw.js`→`lib/pwa/sw-source.js` move + `app/sw.js/route.js` addition; ensure neither pulled the db client into a route-scoped bundle.
4. **Service worker client-side check:** the newly-registered SW at `/sw.js` (scope `/`) can independently cause real browsers to "keep loading" even though curl is fine. Ensure the SW does not intercept/await navigations or `/api/*` in a way that stalls, and after deploying the fix have users hard-refresh / unregister the old SW (incognito) to clear stale SW state.

## Not applicable
No manifest fix (this is not a build/manifest fault). No secret change (MONGO_URL verified correct). No rollback performed. The live app was never taken down.
